# 参考

## 交付 CSV 字段语义

| 列 | 内容 |
|---|---|
| `id` | 原图文件名去扩展名，如 `丁达尔光-4-横屏-9`。批次内唯一。 |
| `prompt` | 取自 pipeline CSV。同一张原图的 3 行 prompt 相同，取任意一行即可（脚本会校验一致性）。 |
| `input_image_path` | 相对批次日期目录，如 `260814-.../4-1707张/丁达尔光-32张/丁达尔光-4-横屏-9.jpg` |
| `output_image_path` / `_1` / `_2` | 相对批次日期目录，如 `260814-...-qt-round1/丁达尔光-4-横屏-9-r1_colormatched.png` |
| `标签` | 光效名，如 `丁达尔光` |

## 路径映射

pipeline CSV 里的路径是 Linux 侧的绝对路径：

```
/ytech_milm/frank/chatgpt_ketu/光照/0820/260814-光影光效-6840-.../4-1707张/丁达尔光-32张/丁达尔光-4-横屏-9.png
```

注意末尾的 `0820` 是**固定的历史前缀**，不随批次目录名变化，0822 批次的路径里也写着 `0820`。所以不能按日期截断路径。`common.rel_from_batch()` 的做法是逐段试探哪一段在批次目录下真实存在，从那一段开始截取，对输入和输出路径都适用，也不受输入根目录层数影响。

## colormatch 配对

每次成功生成产出两个文件：

- `<stem>-rN.png` —— 模型原始输出
- `<stem>-rN_colormatched.png` —— 色彩对齐到原图后的版本

两者成对存在。pipeline CSV 的 `ai_output_image_path` 指前者，`output_image_path` 指后者。失败的行两个文件都没有。脚本选定变体后仍会核对磁盘，缺失就回退到另一个变体。

## 已知的坑

**扩展名不一致**：pipeline CSV 的 `input_image_path` 一律写 `.png`，但磁盘上原图大多是 `.jpg`，还有 `.heic/.webp/.arw/.avif`。0820 那批直接交付后返工，才有了 `0820_光影_final_fixed.csv`。脚本按 `(目录, 文件名主干)` 建索引来定位真实文件。

**目录被改名**：0820 的 pipeline 路径写的是 `4-289张-png`，磁盘上的目录叫 `4-289张`。脚本在按 `(目录, 主干)` 精确命中失败后，会退回到全树按主干唯一匹配，报告里记为「目录名修正」。这个回退只在主干全局唯一时生效，不唯一就报「原图无法定位」。

**嵌套场景目录**：`舞台灯光-1张/音乐-98张/` 这种两层结构存在。只扫一层会漏掉 100 多张，且会把 `音乐`、`舞蹈`、`戏剧` 误当成光效标签。

**目录名里的张数不可信**：`舞台灯光-1张` 底下实际有 112 张，`眼神光-1张` 才是真的 1 张。统计一律以实际文件数为准。

**pipeline 漏跑整个目录**：0822 批次 1707 张原图里，pipeline CSV 只覆盖 1582 张，`极光-31张`、`灯牌-25张`、`台灯-16张`、`弱光-15张` 等整个目录一条记录都没有。这不是生成失败，交付前必须单独提出来。

**失败原因分布**（0822 批次 4746 行中 871 行失败，供判断量级参考）：安全审核拒绝 706、原图超 50MB 上限 122、找不到原图 39、HTTP 413 及网络错误 4。超 50MB 的需要先压缩再重跑。

**垃圾文件**：原图目录里混着 `.DS_Store`、`Thumbs.db`。`common.is_junk()` 负责过滤。

## 编码

模板和交付 CSV 都是 UTF-8 BOM + CRLF。Python 侧读用 `utf-8-sig`，写用 `encoding="utf-8-sig", newline=""`。

Windows PowerShell 控制台默认不是 UTF-8，直接看 Python 的中文 stdout 会是乱码，`chcp 65001` 也不改变 `[Console]::OutputEncoding`，所以脚本一律同时写报告文件，看报告文件即可。
